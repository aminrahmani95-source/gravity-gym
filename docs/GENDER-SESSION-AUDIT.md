# گزارش حسابرسی معماری تفکیک جنسیتی و سانس‌های ورزشی (Gender Access & Gym Sessions Audit)
**سیستم پلتفرم اشتراک ورزشی گراویتی (Gravity Multi-Gym Platform)**  
**تاریخ گزارش:** ۲۹ سپتامبر ۲۰۲۶ (۸ مهر ۱۴۰۵)  
**وضعیت:** حسابرسی اولیه کامل (Pre-Implementation Architectural Audit)  

---

## ۱. خلاصه مدیریتی (Executive Summary)

با توجه به الزامات قانونی و ساختار بازار باشگاه‌های ورزشی در ایران:
1. برخی باشگاه‌ها **کاملاً مردانه (MALE_ONLY)** هستند.
2. برخی باشگاه‌ها **کاملاً زنانه (FEMALE_ONLY)** هستند.
3. برخی مجموعه‌ها **مشترک دوگانه (MIXED)** هستند؛ اما تفکیک زمانی دقیق دارند (سانس بانوان و سانس آقایان کاملاً مجزا و بدون هم‌پوشانی زمانی).

این حسابرسی فنی برای ارزیابی جامع کدهای فعلی بک‌اند، دیتابیس PostgreSQL، موتور درون‌حافظه‌ای (In-Memory Engine)، سیستم احراز هویت، اعتبارسنجی ورود (QR Check-in) و فرانت‌اند تدوین شده است تا مدل **Gender Access + Gym Sessions** با رعایت اصول زیر پیاده‌سازی شود:
* **تغییرناپذیری کامل مدل اقتصادی و قیمت‌گذاری:** هیچ تغییری در قیمت پلن‌ها، ارزش ریالی اعتبارات، تسویه بستانکاری باشگاه‌ها، نامساوی محدودیت طلایی ($\lambda \le 32,000$) و حاشیه سود پلتفرم ایجاد نخواهد شد.
* **حفظ ۱۰۰٪ امنیت مکانیزم بارکد پویا (QR):** اعتبار زمانی ۴۵ ثانیه‌ای، امضای رمزنگاری شده HMAC-SHA256، قفل توزیع‌شده Redlock، ذخیره نانس در Redis و لایه رول‌بک دیتابیس دست‌نخورده باقی می‌ماند.
* **اعتبارسنجی قطعی در سمت سرور (Backend Enforcement):** تفکیک جنسیتی و سانس به هیچ عنوان به اعتبارسنجی کلاینت/فرانت‌اند وابسته نخواهد بود و امکان دور زدن (Anti-Bypass) وجود ندارد.

## ۲. وضعیت فعلی دیتابیس و مدل داده (Current Database State)

### ۲.۱. جدول کاربران (`users`)
* **وضعیت در PostgreSQL (`infra/init-db/01-init.sql`):**
  ستون `gender` در حال حاضر تعریف شده و دارای قید کنترل است:
  ```sql
  gender VARCHAR(10) NOT NULL CHECK (gender IN ('MALE', 'FEMALE'))
  ```
* **وضعیت در موتور حافظه‌ای (`database.service.ts`):**
  کاربران پیش‌فرض با جنسیت مشخص مقداردهی شده‌اند:
  * `user-admin`: `MALE`
  * `user-staff`: `MALE`
  * `user-member-1`: `MALE`
  * `user-member-2`: `FEMALE`
* **ثبت‌نام خودکار از طریق OTP (`auth.service.ts`):**
  کاربران جدیدی که با شماره موبایل وارد می‌شوند، به صورت پیش‌فرض با جنسیت `Gender.MALE` ثبت می‌گردند. توکن JWT صادره شامل `gender` در پی‌لود است.

### ۲.۲. جدول باشگاه‌ها (`gyms`)
* **وضعیت فعلی:**
  ستون `access_mode` در جدول `gyms` وجود **ندارد**.
* **نقص شناسایی‌شده:**
  در حال حاضر مشخص نیست که آیا یک باشگاه کلاً زنانه، کلاً مردانه یا مختلط (شیفتی) است. همه باشگاه‌ها صرفاً بر اساس جدول `gym_sans` سنجیده می‌شوند و امکان مسدودسازی باشگاه در سطح سطح دسترسی وجود ندارد.
* **اصلاح لازم:**
  افزودن ستون `access_mode` به صورت:
  ```sql
  access_mode VARCHAR(20) NOT NULL DEFAULT 'MIXED' CHECK (access_mode IN ('MALE_ONLY', 'FEMALE_ONLY', 'MIXED'))
  ```

### ۲.۳. جدول سانس‌های ورزشی (`gym_sans`)
* **وضعیت در PostgreSQL (`infra/init-db/01-init.sql`):**
  جدول `gym_sans` از قبل با فیلدهای زیر طراحی شده است:
  ```sql
  CREATE TABLE IF NOT EXISTS gym_sans (
      id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
      gym_id UUID NOT NULL REFERENCES gyms(id) ON DELETE CASCADE,
      day_of_week SMALLINT NOT NULL CHECK (day_of_week BETWEEN 0 AND 6),
      gender VARCHAR(10) NOT NULL CHECK (gender IN ('MALE', 'FEMALE')),
      start_time TIME NOT NULL,
      end_time TIME NOT NULL,
      capacity INTEGER DEFAULT NULL,
      is_peak BOOLEAN NOT NULL DEFAULT FALSE,
      created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
      CONSTRAINT chk_sans_times CHECK (start_time < end_time)
  );
  ```
* **تقویم هفته در ایران:**
  $0 = \text{شنبه (Saturday)}$ تا $6 = \text{جمعه (Friday)}$.
* **ناهمگونی در Seedهای فعلی (`02-seed.sql` و `database.service.ts`):**
  * در فایل `02-seed.sql` خطوط ۹۵–۹۷ یک سانس روزانه آقایان (`05:00:00` تا `14:30:00`) همزمان با سانس بانوان (`08:00:00` تا `14:00:00`) درج شده بود تا تست‌های قبلی در ساعات کاری روز پاس شوند. این تداخل برای بازار واقعی ایران و باشگاه‌های شیفتی باید بازطراحی و تمیز شود.
  * در `database.service.ts` هر ۴ باشگاه سانس‌های یکسانی دارند:
    * بانوان: ۰۸:۰۰ تا ۱۴:۰۰
    * آقایان: ۱۴:۳۰ تا ۲۳:۵۹:۵۹ و ۰۰:۰۰ تا ۰۵:۰۰ بامداد
  * هیچ باشگاهی به عنوان تک‌جنسیتی (`FEMALE_ONLY` یا `MALE_ONLY`) تنظیم نشده است.

## ۳. بررسی فرایند اعتبارسنجی ورود و چک‌این (Check-in Validation Audit)

فایل `apps/api/src/modules/checkin/checkin.service.ts` خطوط ۱۴۱–۱۴۴ مرحله پنجم از خط لوله اعتبارسنجی ۸ مرحله‌ای را اجرا می‌کند:
```typescript
// STAGE 5: Gender Schedule & Sans Validation (سانس‌های بانوان و آقایان)
const activeSans = await this.validateActiveGenderSans(targetGymId, user.gender);
```

### نقاط ضعف و ریسک‌های موجود در `validateActiveGenderSans`:
1. **مشکل Timezone محلی سرور:**
   کد فعلی از `new Date().getHours()` و `new Date().getDay()` بر اساس ساعت سیستمی ماشین میزبان استفاده می‌کند. چنانچه سرور در تایم‌زون UTC مستقر باشد، ساعت و روز هفته با تایم‌زون تهران (`Asia/Tehran` با افست +03:30) مغایرت پیدا می‌کند.
2. **عدم بررسی سطح دسترسی باشگاه (`access_mode`):**
   اگر باشگاهی ویژه بانوان باشد (`FEMALE_ONLY`)، سیستم باید قبل از بررسی سانس‌ها، ورود کاربر آقا را با پیام خطای صریح رد کند.
3. **رفتار پیش‌فرض نامناسب در غیاب سانس:**
   کد فعلی خط ۲۹۰ بیان می‌کند:
   ```typescript
   if (sansList.length === 0) {
     return { isPeak: false };
   }
   ```
   اگر برای یک روز یا یک باشگاه هیچ سانسی ثبت نشده باشد (مثلاً جمعه)، سیستم اجازه ورود صادر می‌کند! در مدل تفکیک جنسیتی ایران، اگر برای روز جاری هیچ سانسی برای جنسیت کاربر وجود نداشته باشد، ورود باید قطعاً رد شود (`ForbiddenException` یا `BadRequestException`).
4. **تداخل‌های زمانی:**
   اگر کاربری خارج از ساعات سانس مجاز خود یا در حین سانس جنسیت مخالف مراجعه کند، باید خطای مناسب و راهنمای سانس بازگردانده شود.

## ۴. بررسی کاوش باشگاه‌ها (Gym Discovery Audit)

### ۴.۱. سرویس `gyms.service.ts`
* فیلتر `gender` در کوئری جستجو وجود دارد (`findAll(query: GymDiscoveryQuery)`):
  * در SQL: `EXISTS (SELECT 1 FROM gym_sans s WHERE s.gym_id = g.id AND s.gender = $param)`
  * در In-Memory: فیلتر بر روی جدول `gym_sans`.
* **نقص‌های کاوش:**
  1. باشگاه‌های `MALE_ONLY` و `FEMALE_ONLY` بر اساس ستون اختصاصی فیلتر نمی‌شوند.
  2. اطلاعات سانس امروز (ساعات شروع و پایان سانس جاری برای جنسیت کاربر) در پاسخ کارت باشگاه ارسال نمی‌شود و کاربر در صفحه اصلی متوجه نمی‌شود که آیا همین الان باشگاه برای او باز است یا خیر.
  3. کاربران لاگین کرده در فرانت‌اند باید به صورت پیش‌فرض باشگاه‌های متناسب با جنسیت پروفایل خود را مشاهده کنند.

## ۵. بررسی پنل مدیریت (Admin Management Audit)

### ۵.۱. وضعیت فعلی پنل ادمین
* کنترلر `admin.controller.ts` در حال حاضر فقط متدهای `getMetrics()` و `getRecentCheckins()` را دارد.
* سرویس `economics.service.ts` متد ویرایش تعرفه مالی (`updateGymPricing`) را دارد.
* **نقص:**
  هیچ API و واسط کاربری (UI) برای موارد زیر وجود ندارد:
  1. مشاهده و ویرایش `access_mode` باشگاه (`MALE_ONLY`, `FEMALE_ONLY`, `MIXED`).
  2. تعریف، حذف و ویرایش سانس‌های هر روز هفته (`day_of_week`, `gender`, `start_time`, `end_time`, `capacity`, `is_peak`).
  3. اعتبارسنجی عدم تداخل سانس‌ها برای یک جنسیت در یک روز و رعایت شرط $start\_time < end\_time$.

## ۷. برنامه اقدام گام‌به‌گام (Step-by-Step Implementation Roadmap)

1. **انطباق تایپ‌های اشتراکی (`packages/shared-types`):**
   * تعریف `GymAccessMode = 'MALE_ONLY' | 'FEMALE_ONLY' | 'MIXED'`.
   * افزودن `accessMode: GymAccessMode` به اینترفیس `Gym`.
   * افزودن اینترفیس مدیریت سانس `CreateGymSansDto` و `UpdateGymSansDto`.
2. **بروزرسانی لایه پایگاه داده و Seedها:**
   * افزودن ستون `access_mode` به `infra/init-db/01-init.sql`.
   * همگام‌سازی `apps/api/src/common/database/database.service.ts` (افزودن فیلد به جدول و ساختار اشیاء).
   * تنوع‌بخشی به داده‌های پیش‌فرض:
     * باشگاه ۱ (کارو): `FEMALE_ONLY`
     * باشگاه ۲ (ستاره ونک): `MALE_ONLY`
     * باشگاه ۳ (اکسیژن رویال): `MIXED`
     * باشگاه ۴ (اسپیناس پالاس): `MIXED`
   * درج سانس‌های ۲۴ ساعته واقعی و بدون تداخل برای اطمینان از پاس شدن تست‌های E2E خودکار در هر ساعت از شبانه‌روز.
3. **پیاده‌سازی ماژول مدیریت سانس در ادمین:**
   * افزودن اندپوئینت‌های CRUD سانس‌ها و تغییر `access_mode` باشگاه به `admin.controller.ts` و `admin.service.ts`.
   * اعتبارسنجی دقیق فرمت زمان، روز هفته، و عدم هم‌پوشانی بازه‌های زمانی یک جنسیت.
4. **تقویت منطق اعتبارسنجی در `checkin.service.ts`:**
   * تبدیل زمان به افست رسمی تهران (`Asia/Tehran`).
   * بررسی `gym.access_mode` در ابتدا، سپس تطبیق دقیق با سانس فعال در جدول `gym_sans`.
   * برگشت خطاهای شفاف و محترمانه به زبان فارسی.
5. **ارتقای کاوش باشگاه‌ها در فرانت‌اند (`apps/web`):**
   * نمایش وضعیت سانس جاری و برچسب‌های تفکیک جنسیتی روی کارت هر باشگاه.
   * فیلتر خودکار بر اساس جنسیت کاربر لاگین کرده با امکان سوییچ دستی.
   * افزودن بخش مدیریت دسترسی و سانس‌ها در تب اختصاصی پنل ادمین.
6. **تست‌های جامع و اعتبارسنجی نهایی:**
   * اجرای مجدد ۷ مجموعه تست رگرسیون.
   * ایجاد تست اختصاصی ۱۰ سناریوی مرزی.
   * تدوین مستند نهایی `docs/GENDER-SESSION-IMPLEMENTATION.md`.
